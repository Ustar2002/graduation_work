# 교수님 미팅 정리 (2026-11, M1~M2c 완료 시점)

> 결과 표의 숫자는 2026-11-09 교차 측정 재실행 기준. 상세 기록은 `docs/decisions.md`, 행 단위 데이터는 `results/runs.csv`.

## 1. 한 줄 요약

"같은 계산 과제를 세 가지 언어(NumPy, 순차 C, OpenMP C)로 LLM에게 짜게 하고, 자동으로 채점·시간 측정하는 장치를 만들어 12개 커널 × 3언어 × 5샘플 = 180개 코드를 실제로 돌렸다. 결과: 정확성은 언어보다 **과제 종류**에 따라 갈렸고, 속도 격차는 '라이브러리에 맡길 수 있는 과제냐'로 설명된다."

## 2. 무엇을 만들었나 (쉽게)

- **채점 기계(하네스)**: 프롬프트를 LLM에 보내 코드를 받고 → 코드만 꺼내서 → 컴파일하고 → 별도 프로세스에서 실행해 → 정답과 비교하고 → 맞으면 시간을 재고 → 한 줄의 기록(열 115개)을 남긴다. 사람이 손대는 단계가 없다.
- **공정한 시간 측정을 위해 한 일**: CPU의 빠른 코어 4개에 고정, 거버너 performance, 워밍업 3회 뒤 10회 중앙값, 모든 언어에 같은 컴파일 옵션·같은 정보, 측정 때마다 부하·온도·클럭 기록. 기준선(비교 대상)은 커널과 **같은 프로세스에서 번갈아** 호출해 같은 순간의 속도를 비교한다.
- **오류 분류**: 실패를 9가지로 자동 분류한다(컴파일 오류, 크래시, 시간 초과, 틀린 출력, 수치 불안정, 인자 순서 오류, 메모리 오류, 경쟁 상태, 시그니처 위반). 분류 규칙은 실험 전에 고정했고, 가짜 답안 11종으로 검증했다.
- **과제 12개**: 1단계 GEMM·Jacobi·SpMV·dot, 2단계 histogram·prefix scan·n-body·sort, 3단계 Cholesky·Floyd–Warshall·BFS·FFT. 각각 수학 정의·입출력 계약·크기·허용오차를 영어 명세로 쓰고, 모델에게 그대로 준다.
- **모델**: Claude Sonnet 5.5 한 종류(과제당 5샘플). 총 비용 약 5달러.

## 3. 결과 (통과 수 / 기준선 대비 속도비 중앙값, 과제당 5샘플)

속도비 = 기준선 시간 ÷ 생성 코드 시간. 1.0 이면 기준선과 같은 속도, 0.5 면 절반 속도. 기준선은 과제마다 하나씩 고정: gemm·dot·sort·cholesky·fft 는 NumPy 라이브러리 함수, 나머지는 손으로 쓴 C+OpenMP.

| 과제 | numpy | c_seq (순차 C) | c_openmp (병렬 C) |
|---|---|---|---|
| gemm | 5/5, 0.94 | 5/5, 0.35 | 5/5, 0.87 |
| jacobi2d | 5/5, 0.22 | 5/5, 0.71 | 4/5, 1.45 |
| spmv_csr | 5/5, 0.13 | 4/5, 0.35 | 5/5, 1.03 |
| dot | 5/5, 1.44 | 5/5, 1.03 | 5/5, 1.67 |
| histogram | 5/5, 0.19 | 5/5, 0.54 | 5/5, 1.52 |
| scan | 5/5, 0.15 | 5/5, 0.75 | 3/5, 1.15 |
| nbody | **0/5**, – | 5/5, 2.47 | 5/5, 7.95 |
| sort | 5/5, 1.10 | 5/5, 0.69 | 4/5, 1.28 |
| cholesky | 5/5, 3.43 | 5/5, 2.88 | 4/5, 4.85 |
| floyd_warshall | 5/5, 0.08 | 4/5, 0.99 | 3/5, 1.43 |
| bfs | 5/5, 0.17 | 3/5, 0.73 | 5/5, 1.00 |
| fft | 5/5, 1.05 | 4/5, 2.90 | 5/5, 6.65 |
| **합계 통과** | **55/60** | **55/60** | **53/60** |

실패 17건의 종류: 출력 형식 위반(코드 블록을 안 씀) 4, C 알고리즘 버그(틀린 출력) 7, numpy 수치 불안정 5(전부 nbody), 경쟁 조건 0, 크래시 1.

## 4. 발견한 것 (주장할 수 있는 것)

1. **통과율은 언어 간 차이가 거의 없다(55/55/53).** 실패는 언어가 아니라 **과제 종류**에 몰린다: numpy 는 nbody 한 과제에서 5/5 실패(수치 상쇄), C 는 Tier 3 의 복잡 알고리즘(블록화 Floyd–Warshall 3건, bottom-up BFS 2건, 블록 Cholesky 1건, FFT 메모리 오류 1건)에서 실패. "복잡한 알고리즘을 재구성하려다 정확성을 잃는다"는 Tier 3 의도가 그대로 나타났다.
2. **속도 격차는 "라이브러리에 맡길 수 있는가"로 설명된다(핵심 가설 지지).** 라이브러리 한 줄로 끝나는 과제(gemm, dot, sort, fft, cholesky)에서 numpy 는 기준선과 같거나 더 빠르다(0.94~3.43). 라이브러리가 단일 스레드이거나 어색한 과제(jacobi2d, spmv, histogram, scan, floyd_warshall, bfs)에서는 numpy 가 기준선의 8~22 % 에 그친다. 같은 과제에서 병렬 C 는 기준선과 비슷하거나 더 빠르다.
3. **모델은 C 에서 성능 결정을 직접, 그리고 공격적으로 내린다.** GEMM 10/10 이 블록화·패킹·AVX2 마이크로커널, nbody 10/10 이 SoA 변환 + rsqrt 근사 + AVX2, scan 은 코드가 추출된 9개 모두 AVX2, FFT 는 10개 중 9개가 four-step 분해(1개는 Stockham radix-4). 그 결과 nbody·cholesky·fft 에서 병렬 C 가 기준선의 5~8배인데, 이는 기준선이 약한 탓도 있다(§5).
4. **수치 결정의 축이 따로 있다.** dot 에서는 15개 구현 전부(C 10개는 다중 누산기, numpy 5개는 `np.dot` 위임)가 float32 누적 함정을 피했고, nbody 에서는 numpy 5/5 가 행렬곱 재배열(큰 항끼리의 상쇄)로 실패했다. FFT 에서는 10/10 이 double 트위들을 택해 float32 점화식 함정을 피했다. "성능 결정을 누가 내리나"에 더해 "수치 결정을 누가 내리나"가 결과를 가른다.
5. **numpy 에서 모델이 반복하는 헛수고**: histogram·scan 에서 10/10 이 라이브러리 함수를 `threading` 으로 쪼개 병렬화하려 했지만 효과가 없었다(단일 스레드 메모리 바운드).
6. **추론(thinking)은 FFT C 에서만 발동**(10/10, 커널당 4~13k 토큰); 나머지 170개 응답은 추론 없이 답했다.

## 5. 한계와 주의 (먼저 말해 두면 좋은 것)

- **모델 1종, 언어 3종, 샘플 5개**: 예비 연구다. pass@5 는 거의 모든 칸이 1.0 이라 변별력이 없고, 통과율 차이(55 vs 53)는 통계적으로 의미 없다.
- **기준선의 세기가 과제마다 다르다**: OpenBLAS 의 float32 Cholesky(15 GFLOPS)와 pocketfft(단일 스레드)는 약한 기준선이라 cholesky·fft 의 5~8배는 "라이브러리보다 빠르다"지 "최적"은 아니다. nbody 기준선은 sqrtf 기반 단순 C 라 rsqrt 근사 코드가 8배 빠르다.
- **노트북 측정**: 지속 부하 뒤 CPU 클럭이 절반으로 떨어지는 현상이 있어 절대 시간은 2배까지 흔들린다. 커널과 기준선을 같은 프로세스에서 번갈아 재는 방식으로 바꿔 **속도비**는 안정시켰지만, 최종 수치는 데스크탑·서버에서 다시 재는 것이 맞다.
- **프롬프트가 하드웨어 사실을 알려 준다**(코어 4개, AVX2, 캐시, 컴파일 명령). 이것이 모델의 결정에 영향을 준다. 공개하지 않는 조건과의 비교는 아직 없다.
- **temperature 를 고정하지 못했다**: Claude 5.x 는 temperature 를 받지 않아 제공자 기본 샘플링을 썼다(effort medium 고정).
- 측정 규약을 실험 중간에 두 번 고쳤다(부하 평균 플래그, 교차 측정). 모든 행은 고친 규약으로 다시 쟀고 이전 숫자는 git 이력에 있다.

## 6. 교수님께 물어볼 것

1. **다음 축 선택**: M3(언어 확장: numba, halide, rust)로 갈지, 지금 3개 언어에서 **마이크로 조건**(M4: 하드웨어 정보 비공개, 수정 루프 compiler vs compiler+lint, 키워드 인자)을 먼저 볼지. 예비 연구 보고서에 어느 쪽이 더 설득력 있는지.
2. **기준선 정책**: "라이브러리가 있으면 라이브러리" vs "모두 손으로 쓴 최적 C" — 약한 라이브러리 기준선(cholesky, fft)을 그대로 둘지, 더 강한 기준선(예: MKL, FFTW)을 추가할지.
3. **모델**: Sonnet 5.5 하나로 계속할지, Opus 5.5 를 두 번째 모델로 넣어 "모델이 강해지면 언어 차이가 줄어드는가"를 볼지(비용은 전체 180회 기준 약 10달러).
4. **실험 머신**: 연구실 서버·데스크탑을 쓸 수 있는지(노트북 클럭 문제). 쓸 수 있다면 같은 하네스로 다시 재는 데 1~2시간.
5. **nbody 의 numpy 전멸을 어떻게 볼지**: 모델의 수치 판단 실패로 보고할지, 과제 설계(연화 상수 포함 자기 항)가 가혹했다고 볼지. 허용오차(1e-3)는 직진 구현이 500배 여유로 통과하는 수준이다.
6. **린트 플러그인(인지프)**: 하네스에 쌓인 180개 커널과 17개 실패 라벨을 린트 평가 데이터로 쓰는 계획이 괜찮은지, 어떤 라벨이 더 필요한지.
7. 보고서 범위: 12개 커널 결과를 다 넣을지, Tier 1~2 중심으로 좁힐지.

## 7. "어디까지 했다"고 말할 것

- 하네스 완성: 생성·추출·빌드·격리 실행·분류·측정·CSV·집계 전 과정 자동화, 단위 테스트 262개, 측정 규약 코드로 강제(코어 고정, 거버너 확인, 부하·클럭·온도 기록, 교차 기준선).
- 과제 12개 명세·참조·테스트·기준선 완성(3단계).
- 실제 실험 1차 완료: 12과제 × 3언어 × 5샘플 = 180개 생성 코드, 총 비용 약 5달러, 결과 CSV 189행(열 115개) 과 raw 응답 전부 보관.
- 주요 결과: 통과율 55/55/53, 속도 격차는 라이브러리 위임 가능성으로 설명, 수치 결정 축 발견(nbody·dot·fft).
- 미완: 언어 확장(numba/halide/rust), 마이크로 조건·수정 루프, 안전성(ASan/린트), 성능 결정 자동 요약(perf_summary), 그래프.
