## 2026-11-04 (리뷰 반영: classify·worker)

- **§10 v2.1 순서를 코드에 반영**(`harness/classify.py`): NaN/Inf → pass → arg_order(`transposed_output` → `swapped_operands`(M==N==K) → `column_major_all` → `swapped_MN_dims`) → 센티널·계약 → imprecise → mismatch. 결과: 정사각 `B@A`는 `column_major_all`이 아니라 `swapped_operands`로 보고되고, `C[i*M+j]` 커널은 실제 rect(200,130,312)에서 센티널·OOB가 남아도 `arg_order`/`swapped_MN_dims`다(`n_unwritten`·`oob_write`는 metrics에 유지; metrics에 `oob_write` 키 추가 — 추가 키라 소비자 영향 없음). 부수 효과: 센티널 일부 + NaN은 이제 `nan_inf`(규칙 1이 먼저).
- **규칙 4 내부 순서 고정: 전부 센티널 → `accumulated_into_c` → `partial_write` → `out_of_bounds_write`**. 근거: float32에서 `-2048 + ref`는 |ref| < 2⁻¹³이면 정확히 `-2048.0`으로 되돌아가 `n_unwritten`에 세어진다. 실측: `C += A@B`가 small(256³)에서 `partial_write:1/65536`, large(1024³)에서 `partial_write:10/1048576`으로 잘못 기록됐다(tiny·rect는 0개). 진짜 부분 기록은 모든 원소가 `sentinel + ref`와 일치할 수 없으므로 누적 검사를 앞에 둬도 부분 기록을 가리지 않는다. `n_unwritten` 지표의 정의(`count(out == sentinel)`)는 바꾸지 않았다. 이에 따라 누적 + OOB는 `accumulated_into_c`(예전: `out_of_bounds_write`) — 샘플 수준 detail은 `aggregate_sample`이 `oob_write` 플래그를 먼저 보므로 행 결과는 그대로다.
- **출력이 맞고 OOB만 있는 호출**: 규칙 2(pass)가 계약 규칙보다 먼저이므로 `classify_output`은 `pass`를 돌려준다. 워커(`_apply_contract_flags`)가 그 호출을 `wrong_output`/`out_of_bounds_write`로 기록해 bench `error_detail`과 `check_tests`가 비지 않게 한다(`inputs_mutated` 덮어쓰기와 같은 자리; `arg_order` 판정은 OOB가 있어도 유지). 샘플·행 수준은 변화 없음(`aggregate_sample`, run.py pass 정의).
- **워커 `BaseException` 핸들러의 `str(e)` 보호**: `__str__`이 예외를 던지는 예외 객체를 커널이 올리면 핸들러가 죽어 `worker_error`(rc=3) → run.py가 harness_error로 run 전체를 중단했다(실측). `message`/로드 실패 detail은 `<unprintable Type>`으로 대체하고 `traceback.format_exc()`도 같은 방식으로 감싼다.

- **`dot`(STREAM triad 대신)**: reduction 병렬화가 표의 결정 사항이라 dot을 골랐다. `dot(x, y, out, n)`, 결과는 `out[0]`. 입력 uniform[0,1)이라 합이 n/4까지 커진다 — n=2²⁵에서 NumPy float32 내적은 상대오차 1.5e-4로 통과, 단순 float32 순차 누적은 7e-2, 4분할 float32 누적은 6.6e-3으로 실패(실측). **누적 정밀도를 모델의 결정 사항으로 만들기 위한 의도된 설계**다(CLAUDE.md §6의 린트 예시 `numeric/accumulate-in-float32`와 같은 현상). rtol·atol 1e-3. 출력이 스칼라 하나라 `numeric_pattern_tol_ratio`를 500으로 넓혔다(단순 누적 커널이 `numeric_instability`로 분류되는 것 확인). 기준선은 NumPy `np.dot`.
- **입력 크기 기준(순차 C 0.3~3초)과의 차이**: 이 머신의 기준선 중앙값은 gemm 약 9 ms, jacobi2d 113 ms(1스레드 230 ms), spmv_csr 13 ms(1스레드 43 ms), dot 12 ms다. spmv·dot은 기준보다 짧다. 더 키우면 테스트 파일이 GB 단위가 되고 14 GiB 노트북의 워커 메모리 한도(8 GiB)에 걸린다. ms 단위 측정은 M1에서 변동계수 1~10 %로 가능함을 확인했다. → 데스크탑으로 옮기면 다시 정한다.
- **Halide로 표현하기 어려운 커널(sort, BFS, prefix scan)** 은 M3에서 Halide를 넣을 때 정한다(해당 조합 제외 또는 Halide 대상 축소).
- **린트**: 마감과 무관하게 필요해질 때 구현한다(사용자). M1·M2는 빈 결과로 진행.
- **검증**: 단위 테스트 170개 통과. GEMM 더미 회귀 9행이 M1과 같은 분류. 새 과제 3개 × 언어 3개의 정답 더미 9행 모두 pass(기준선 포함 69초).

## 2026-11-09 (M2c — Tier 3 통합: cholesky, floyd_warshall, bfs, fft)

- **구현 방식**: 과제별 에이전트 4개를 동시 실행(지난번 메모리 소진은 반박 단계의 14개 동시 실행이 원인이라 4개로 제한). 리뷰·반박 단계는 생략하고 구현자 보고의 실측·이탈을 아래에 기록한다. 각 과제는 자체 단위 테스트(총 262개 통과)와 워커 실측을 거쳤다.
- **cholesky**: 참조 L 의 RMS 는 모든 형태에서 ≈1.1547(=√(4/3)) → atol ≈ 1.15e-3. 직진 float32 순차 구현 max_tol_ratio tiny 4.7e-5 / rect 5.7e-5 / small 2.2e-4 / large 3.9e-4(여유 500배). 기준선 `np.linalg.cholesky`(OpenBLAS spotrf)는 4스레드 187 ms·1스레드 207 ms(15 GFLOPS)로 **약한 라이브러리 기준선** — 단순 OpenMP 더미가 1.27배 빠르다(nbody 와 같은 해석 주의). §18 의 "대각 우세" 문구는 행합 기준으로는 성립하지 않아 spec 은 "조건수 ≈ 2.3 으로 양호" 로 서술했다. c_openmp 더미는 열이 아니라 행 병렬(row-major 연속 접근).
- **floyd_warshall**: 밀도 0.3·시드 그대로의 tiny(n=5)는 2홉 경로가 하나도 없어 완화를 전혀 시험하지 못했다(복사만 하는 커널이 tiny 통과). **tiny 를 n=8 로 변경**(완화 27쌍·도달 불가 13쌍; test_hash 4e28f52e2f452399 → 2a9ff0da4e20355e). rect 이상에는 도달 불가 쌍이 없다. "정확히 INF" 는 허용오차 안에서 검사된다(2·INF 는 실패). 기준선 C+OpenMP large 48 ms(44 GFLOP/s), c_seq 더미 165 ms, numpy 더미 853 ms. k 루프 병렬화 변형은 3/3 `race_condition`.
- **bfs**: tiny 의 행 길이 상한을 2 로 낮췄다(상한 32 를 n=7 로 클립하면 완전 그래프가 되어 다단계·−1 을 검사 못 함; spec 에 명시). 층화 추출 경계를 정수 산술로 바꿔 이웃 층 충돌 가능성을 없앴다 — **같은 잠재 결함이 `tasks/spmv_csr/gen_tests.py` 에도 있다**(현재 시드에서는 발생하지 않음; 데이터를 바꾸지 않기 위해 그대로 둔다). rect·small·large 에 도달 불가 정점 없음(평균 차수 16). 기준선 C+OpenMP large 103~110 ms, c_seq 큐 BFS 358 ms(1스레드 기준선 413 ms 보다 빠름), numpy 레벨 동기 1,250 ms. 원자 연산 없는 변형은 6/6 `race_condition`.
- **fft**: NumPy 2.3.5 는 complex64 를 승격하지 않아 기준선 complex64 로 통과(ratio ≤ 4.6e-5). 직진 radix-2 float32 + double 트위들 더미 ratio ≤ 5.3e-4. **float32 점화식 트위들 변형은 large(2²²)에서만 실패**(ratio 1.43 → `numeric_instability`) — 트위들 정밀도가 실제 결정 사항. 기준선 pocketfft 단일 스레드 151 ms, c_openmp 더미 98~100 ms, c_seq 198 ms. 센티널 -1e9.
- **`work` 식에 `log2` 허용**(`harness/taskspec.py`).

## 2026-11-11 (측정 결함 — 교차 측정에서 파이썬 커널의 스레드가 CPU 하나에 묶임; 수정 완료, 재측정은 사용자 승인 대기)

- **원인**: 교차 측정(2026-11-09)에서는 기준선이 커널과 같은 프로세스에 로드된다. 기준선이 OpenMP 공유 객체면 libgomp 가 `OMP_PROC_BIND=true` 아래 로드 시점에 주 스레드를 place 0(cpu0)에 묶고, 그 뒤 호출되는 파이썬 커널이 만든 스레드(`threading`, `ThreadPoolExecutor`)가 1-CPU 마스크를 물려받는다. 2026-11-09 의 BLAS 스레드 문제와 같은 메커니즘의 다른 경로다.
- **영향 범위(현재 `results/runs.csv`)**: 스레드를 쓰는 numpy 구현 19행(jacobi2d 5, histogram 5, scan 5, spmv_csr 3, floyd_warshall 1)이 한 코어에서 측정됐다 → 그 칸의 numpy 속도비가 실제보다 낮고 `c_openmp`/`numpy` 비가 과장돼 있다. 재현(powersave, 참고용): scan/numpy/1 이 수정 전 동작에서 145 ms, 수정 뒤 53~59 ms(속도비 0.10 → 0.25). 교차 측정 이전(커밋 d32a609)의 측정에서는 scan numpy 0.38, histogram 0.26 이었다. 통과·실패 판정과 오류 분류는 영향이 없다(check 는 별도 워커).
- **수정**: *호출 친화도*. `call_kernel` 이 호출 직전에 주 스레드 친화도를 그 코드의 규약 집합으로 두고 직후에 되돌린다(둘 다 시간 측정 구간 밖). 규칙(`protocol.call_cpus`, `run.bench_plan`): OpenMP C → 건드리지 않는다(libgomp 의 고정), python → bench 워커의 고정 코어 전체, 순차 C → 고정 코어의 첫 CPU. 워커 CLI `--kernel-cpus`/`--baseline-cpus`(auto | none | CPU 목록), `bench.json` 의 `call_affinity{main_after_load, kernel, baseline, main_after_bench, libgomp, error}`, 실패하면 행 플래그 `call_affinity_failed`. 요청 CPU 가 taskset 집합 밖이면 적용하지 않고 오류로 남긴다. 파이썬 기준선은 고정 코어 전체에서 임포트한다. 행의 `threads`·`cores` 는 커널 호출 동안의 환경(c_seq: 1·"0"), `omp_env` 는 bench 워커가 받은 변수, `cpu_mhz_*` 는 그 코드가 쓴 CPU 에서 읽는다. 환경 지문(env_hash)에 `call_affinity_policy`·`bench_loop_fsync` 를 넣어 규칙이 다른 행이 구분되게 했다. 단위 테스트 262 → 276(파이썬 스레드의 마스크, OpenMP 스레드 배치 유지, 예외 경로 복원, 집합 밖 CPU 거부, 여섯 조합의 실행 계획).
- **순차 C 를 첫 고정 CPU 에 두는 이유**: 프롬프트의 "코어 1개에 고정"과 같고, OpenMP 주 스레드의 place 이자 워커의 주 스레드가 이미 돌던 CPU 라 호출마다 식은 코어로 옮기지 않는다(검토 실측: cpu2 로 옮기면 +36 %). cpu0 의 IRQ 부담은 실측 0.00 % 였다. check 단계의 `single_core`("2")는 그대로다.
- **독립 검토(에이전트 3)**: (1) 의미 — 교차 bench 28회·OpenMP 호출 623회 모두 스레드 4개가 서로 다른 CPU 에 묶여 있고 주 스레드는 place 0. libgomp 는 주 스레드를 다시 묶지 않으므로 복원이 필수다(빼면 병렬 구간 1.9배). (2) 통합 — 더미 파이프라인(gemm·histogram × 3언어)이 여섯 조합 모두 기대한 호출 CPU 로 돌았고 재실행은 멱등. (3) 잔여 간섭 — 아래 후보들. 검토 중 지적된 것(집합 밖 CPU 검증, 복원 오류 기록, threads=1 설정에서의 CPU 선택, 기준선 임포트 순서, 주파수 샘플 대상, 테스트 부족)은 모두 반영했다. 테스트가 수정 과정의 실수 하나(OpenMP 기준선 로드 뒤 libgomp 의 고정을 되돌려 버림)를 잡았다.
- **이 수정이 바꾸는 실행 조건 — 규약 변경이므로 재측정 전에 사용자 승인을 받는다(원칙 5)**: 여섯 조합(커널 × 기준선) 중 셋이 달라진다. ① numpy × C+OpenMP 기준선: 커널의 주 스레드와 그 스레드들이 cpu0 → 고정 코어 전체(버그 수정). ② c_seq × NumPy 기준선: 고정 코어 네 개 위를 떠돌던 것 → 첫 CPU 고정. ③ c_openmp × NumPy 기준선: 기준선 호출의 주 스레드 cpu0 → 고정 코어 전체. ②③은 검토 실측에서 잡음 범위 안이지만 조건이 달라지므로 재측정은 일부가 아니라 **네 run 전체**(`--force`, API 비용 0, 약 25분)로 한다. 재측정 전에 커밋해 `harness_version` 이 깨끗한 해시가 되게 한다. 현재 거버너가 `powersave` 라(재부팅) 사용자가 `performance` 로 바꾼 뒤에 돌린다.
- **검토에서 나온 규약 후보(미적용 — 사용자 승인 필요)**:
  - (a) **`OMP_WAIT_POLICY=passive` 고정**. 이 머신에 실제로 로드되는 libgomp(패키지 libgomp1 16, gcc 15 가 아님)는 하이브리드 CPU 에서 스핀 대기 기본값을 1 로 둬 병렬 구간 뒤 작업 스레드가 스핀하지 않는다(실측 0.03~0.23 ms). 비하이브리드 기본값(300000)이면 40~47 ms 스핀하며, 그 상태에서는 OpenMP 호출 직후의 numpy 커널이 52~84 %, BLAS 기준선이 2.4배 느려진다. 지금은 우연히 안전한 상태이므로 다른 머신으로 옮기기 전에 고정하는 것이 낫다. 여기서는 수치상 중립(floyd_warshall c_openmp 47.2/94.4 → 47.8/94.7 ms). `omp_env`·env_hash 가 바뀌고, 프롬프트에 알리지 않는 환경 변수가 하나 늘어난다.
  - (b) **bench 루프 안의 fsync 제거**(`measurement.bench_loop_fsync: false`; 기본 true = 현행). 호출 쌍 사이에 진행 기록 fsync 가 두 번(합계 13~20 ms 추정) 끼어 쌍의 첫 호출만 유휴 뒤에 시작한다. 7~12 ms 짜리 호출에서 유휴 뒤 절반이 10~40 % 느리다(gemm c_openmp 기준선 8.3~10.2 ms 대 7.0~7.7 ms). 기준선과 같은 호출인 gemm/numpy 의 속도비가 0.89~1.20 으로 퍼진 원인으로 보인다(fsync 가 없는 tmpfs 에서는 0.992~1.003). performance 거버너에서 A/A(기준선 대 기준선) 확인 뒤 적용 여부를 정한다.
  - (c) **호출 사이 정착 대기(settle)는 채택하지 않는다**. 20 ms 대기는 모든 호출을 식은 상태로 만들어 속도비를 −7~+31 % 옮기고 A/A 산포를 ±0.5 % → ±7.5 % 로 키웠다(검토 실측). 시험용으로 넣었던 옵션은 지웠다.
  - 주파수 결합(4스레드 호출 직후의 1스레드 호출이 느려짐)은 performance 거버너의 정상 행에서 약 1 %, drift 플래그 행에서 14~30 % 다 — 기존 `baseline_drift` 플래그가 잡으므로 루프는 바꾸지 않는다.

## 2026-11-12 (M3 사전 검증 결과와 언어별 통합 결정)

언어마다 에이전트 하나가 작은 커널(dot·gemm·histogram 등)을 손으로 써서 실제 워커로 import·check·교차 bench 까지 돌려 보고 통합 설계를 냈다(산출물: 세션 임시 폴더 `m3/designs/<언어>.json`; 아래는 채택한 결정).

- **공통**: 모든 새 언어를 기존 워커의 두 백엔드에 얹는다 — numba·halide 는 `python`(모듈 import), rust·mojo 는 `c`(ctypes 로 C ABI 공유 객체). 측정 루프·교차 측정·호출 친화도는 그대로 쓴다. 언어별 런타임 스레드 수는 환경 변수로 `measurement.threads` 에 고정한다(`NUMBA_NUM_THREADS`, `HL_NUM_THREADS`, `RAYON_NUM_THREADS`; Mojo 는 런타임이 친화도 마스크에서 정한다).
- **numba**: 진입 함수 자체가 명시 시그니처의 `@numba.njit(...)`(배열 `float32[::1]`·`float32[:, ::1]`, 차원 `int64`, 반환 `void`) — import 때 한 번 컴파일되고 호출 중에는 컴파일하지 않는다. 빌드 단계(AST)에서 모든 njit/jit 에 시그니처가 있는지, 워커에서 디스패처가 하네스의 인자 타입을 컴파일 없이 받는지 검사한다. 스레딩 계층은 `omp`(C+OpenMP 기준선과 같은 libgomp 하나를 공유; workqueue 는 6~35배 느렸다) — 그래서 numba 는 OpenMP 런타임을 쓰는 언어로 취급한다(OpenMP 환경 변수, 호출 친화도는 libgomp 고정 그대로). `cache=True` 금지, SciPy 가 venv 에 있으면 안 된다(njit 안의 `np.dot` 등이 BLAS 를 부르게 됨 — 정적 검사에 넣는다). 12개 과제 모두 가능(bfs 는 어색).
- **halide_auto / halide_manual**: 모델은 알고리즘 모듈(`algo.py`)을 쓰고, 하네스가 정확한 과제 시그니처의 `kernel.py` 래퍼를 만든다. import 때 파이프라인을 만들어 auto 는 모델이 쓴 스케줄 지시를 무시·기록하고 자동 스케줄러를 적용, manual 은 모델의 스케줄 그대로 JIT 컴파일한다. 호출은 numpy 버퍼를 복사 없이 감싸 호출자의 출력 버퍼에 실현한다. **자동 스케줄러는 Li2018**(parallelism = threads): Adams2019 와 속도가 비슷하고(기하평균 1.38 대 1.36) 132번 컴파일에서 한 번도 실패하지 않았다(Adams2019 는 잡을 수 없는 abort 가 난다). Adams2019·Mullapudi2016 은 같은 응답을 다시 재는 민감도 분석으로 남긴다(API 비용 0). **과제 10개**: sort·bfs 는 Halide 로 표현할 수 없어 제외. jacobi2d·spmv_csr·floyd_warshall·cholesky·fft 는 "언어가 순차 알고리즘을 강제하는 어색한 과제"로 분석에서 따로 묶는다. 비대칭(기록): auto 는 호출 형태마다 자동 스케줄을 다시 짜고, manual 은 한 스케줄이 모든 형태에서 맞아야 한다.
- **rust**: `{backend: c}` + 샘플마다 고정 템플릿의 cargo 크레이트 — edition 2021, rayon =1.12.0(Cargo.lock 고정, 오프라인 `--frozen`), opt-level 3, codegen-units 1, LTO 없음, panic=abort, `-C target-cpu=native`, `-Wl,--no-undefined`. run 당 의존성을 한 번 미리 빌드하고 샘플마다 `cargo clean -p kernel`(공유 target 디렉터리의 묵은 산출물 방지). panic(경계 검사 등)은 `runtime_crash` + 상세 `rust_panic:<메시지>` 로 기록한다(오류 분류표는 고정; 안전성 분석에서 따로 셀 수 있게). 기록할 차이: gcc 는 `a*b+c` 를 기본으로 FMA 로 합치지만 rustc 는 하지 않는다 — Rust 에서는 FMA 가 모델의 결정이다.
- **mojo**(사용자 결정 2026-11-12): `{backend: c}` + `mojo build --emit shared-lib`(`@export` C ABI, 차원은 `Int32` — `Int` 차원은 ctypes 가 조용히 받아 값이 깨지는 것을 확인해 소스와 LLVM IR 두 단계로 검사). **4스레드**: Mojo 1.2 표준 라이브러리에 CPU 병렬화가 없어 `max==26.7.0` 을 설치했다(`max.algorithm.parallelize`; 약 125 MB, numpy 고정). 런타임 대기 `MODULAR_THREAD_BUSY_WAIT_US=0`, 작업 스레드 코어 고정 `MODULAR_ENABLE_AFFINITY=1`, 워커가 커널·기준선 로드 전에 Mojo 런타임을 미리 초기화(그러지 않으면 libgomp 의 1-CPU 마스크를 물려받아 4.6배 느렸다). **문법 안내**: Mojo 는 1.1 에서 `fn`·`alias` 가 없어지는 등 바뀌어, 100줄 이내 문법 안내(`prompts/hints/mojo.md`, 모든 예제 컴파일 확인)를 붙인 조건을 비교의 주 조건으로 쓰고, 안내 없는 조건도 한 번 돌려 숙련도 효과를 따로 잰다(추가 60회). abort·경계 검사 실패(SIGILL, stdout 출력)는 stdout 위반이 아니라 `runtime_crash` + 상세 `mojo_abort` 로 분류한다.
- **Mojo 사용 통계(개인정보)**: `mojo build` 는 기본 설정으로 매번 telemetry.modular.com 에 연결한다(사전 검증에서 strace 로 확인). 사용자 승인으로 `~/.config/modular/modular.cfg` 에 사용 통계·충돌 보고를 끄는 설정을 썼고, 빌드의 외부 연결이 0회인 것을 확인했다. 하네스도 `MODULAR_HOME`(run 별 디렉터리, 같은 설정)을 따로 준다. 그 전의 사전 검증 빌드 일부는 기본 설정으로 돌아 통계가 전송됐을 수 있다.
- **설치(추가)**: max 26.7.0(max-core, max-shmem-libs, msgspec, psutil, rich 등). numpy 2.3.5·SciPy 없음 유지.
